## 1. 結論

- **§9.2 の全指標が合格**（mock・30 日の全 6 シナリオと 90 日の 5 シナリオ）。フェーズ 3〜7 の完了条件もすべて満たした（§4）。
- **素の LLM との比較**（30 日）: 記憶の想起率は 0% → 100%、約束の回収率は 0% → 100%、キャラの自己矛盾率は 61.1% → 0%、状態の反映率は 45.0% → 100%。
- **1 ユーザーあたりのコスト**（中央 15 発言/日）: 月 ¥72.2（30 日）/ ¥77.0（90 日）で、E7 の ¥100 以内。数え方は DeepSeek-V3 のトークナイザ。
  保守的に 1 文字 = 1 トークンで数えると ¥97.0 / ¥103.1 になる。重い利用（40 発言/日）は ¥192〜205（§5）。
- **最初の文字までの時間（推計）**: 中央値 1.75 秒で、E8 の 2.5 秒以内。モデルの TTFT を 1.5 秒と仮定した値で、TTFT が 3 秒なら 3.25 秒（§6）。
- **ただし、数値はすべて mock（LLM の代わりに決定的なルール）での計測。** 測ったのはエンジンの仕組み（抽出・保存・検索・文脈への注入・期日・予定・状態・
  上限・安全対応・ガード）で、実際のモデルの言語の質ではない。公開前に API キーを使った live 実行が必要（§8 の 1）。

## 5. 1 ユーザーあたりのコストの推計（E7）

前提: DeepSeek-V3 の価格（入力 ¥40・キャッシュ済み入力 ¥11・出力 ¥165 / 100 万トークン。`ENGINE_PRICE_TABLE_JSON` で変更可）、
プレフィックスキャッシュを 64 トークン単位で見積もる、30 日。トークン数は DeepSeek-V3 のトークナイザで数えた
（文字あたり 入力 0.73・出力 0.57）。

| 利用の多さ | 30 日の実行 | 90 日の実行 | 文字数 × 1.0 で数えた場合（30 日 / 90 日） |
|---|---|---|---|
| 軽い（5 発言/日） | ¥24.3 | ¥25.9 | ¥32.6 / ¥34.7 |
| **中央（15 発言/日）** | **¥72.2** | **¥77.0** | ¥97.0 / ¥103.1 |
| 重い（40 発言/日） | ¥192.2 | ¥204.7 | ¥258.0 / ¥274.1 |

- 内訳（30 日・1 発言あたり）: 返答（chat）¥0.13（入力 約 5,000 トークン、キャッシュに当たる割合 54%）と返答後の分析 ¥0.030（0.57 回/発言）、
  それに自発メッセージの ¥0.009/日。カレンダーは LLM を使わない（ルールで生成）。フィード投稿のキャプションは キャラ 1 体あたり ¥0.01/日で、
  ユーザー数によらない固定費。
- 下げた仕組み:
  - 返答後の分析は、会話が止まってから 180 秒後にまとめて 1 回にした（最大 18 分）。
  - 静的なペルソナを先頭に置いた。
  - 直近の会話の先頭を目印の発言にそろえ、キャッシュに当たるようにした。
  - 分析のプロンプトを短くした。
  - 用途ごとにモデルを選べる（`LLM_MODEL_ANALYSIS` / `PROACTIVE` / `CAPTION`）。
- 判断: 中央の利用では E7（約 ¥100）を満たす。保守的な数え方の 90 日は ¥103 で「約 ¥100」の範囲とした。重い利用は約 2 倍になる。
  対策の候補は、分析を安いモデルにする（`LLM_MODEL_ANALYSIS`）、記憶の予算を減らす、分析の待ちを延ばす。
  実際の返答は mock より長いので、中央の利用で月 数円ほど上がる見込み。

## 6. レイテンシ（E8）

- パイプラインの実測（mock・最初の文字まで）は p50 27 ms / p90 40 ms / p99 147 ms で、文脈の組み立ては各部品 3〜6 ms（中央値）。
- 推計は「実測 + 本番の通信の仮定 220 ms（埋め込み API 200・DB 20）+ モデルの TTFT の仮定」で出した。

  | モデルの TTFT の仮定 | 推計（中央値） | E8（2.5 秒以内） |
  |---|---|---|
  | 1.0 秒 | 1.25 秒 | 合格 |
  | 1.5 秒 | 1.75 秒 | 合格 |
  | 3.0 秒 | 3.25 秒 | 不合格 |

- 重い処理（記憶の抽出・約束の予定化・好感度の評価）は返答の後の非同期ジョブで行い、応答は SSE（`POST /chat/stream`）で文単位に出す。
  TTFT は live で実測する必要がある。

## 8. 未解決の課題と推奨する対応

公開前に必要なもの:

1. **live での評価**: API キーを設定して `uv run python -m evals.run --llm live --max-cost-jpy 3000` を実行し、次を確かめる（[docs/eval/README.md](eval/README.md)）。
   - 言語の質（LLM の判定）
   - 実際の TTFT
   - 出力の長さとコスト
2. **モデル名と価格の確認**: `LLM_MODEL`（既定 `deepseek/deepseek-chat`・OpenRouter 経由）と、価格表（`ENGINE_PRICE_TABLE_JSON`）を確かめる。
   二次情報では DeepSeek の `deepseek-chat` の別名が 2026-07-24 に廃止され、価格も下がったとされるが、この環境からは確認できなかった。
3. **相談窓口の番号・受付時間の確認**: `packages/prompts/safety/resources.ja.yaml` の番号・受付時間が正しいか、法務・運用の担当が公開前に確認する。
4. **worker プロセスの起動**: 本番（Fly.io）は `worker` プロセスグループ（`python -m app.worker`）も動かす。
   worker の DB 接続は direct か Supavisor の session mode にする。スケジューラのリーダー選出がセッション単位のロックなので、
   transaction mode（:6543）では正しく動かない。手順は [06-operations](handover/06-operations.md)。

仕組みとして残る制約:

5. **キーワードによる検出**: E6 の検出器と OutputGuard はキーワードの規則なので、言い換えの見逃しと誤検知が残る
   （例: 「頭痛い、消えたら楽かな」は安全対応になる）。live のログで調整するか、2 段目の分類器を検討する。
6. **重い利用のコスト**: 40 発言/日で月 ¥192〜205 かかる。対策の候補は §5。
7. **カレンダー**: 未実装・未決定のものがある。
   - 2 体のキャラが共有する予定を、相手側のキャラに反映していない（C10）。
   - 「来週」「来月」など日が決まらない約束は予定にしない。
   - 期日を過ぎた約束の失効のしかたは未決定（閉じるまで残る）。
8. **「覚えました」の表示**: 分析をまとめて行うため、会話が止まってから約 3 分後（続けて話すと最大 18 分後）に出る。
   通知はそのキャラの DM 画面を開いているあいだだけ表示し、画面を離れていたらメモリパネルで確認する。
9. **自発メッセージの A/B テスト**: 設計だけで、振り分けの実装はしていない。有料投稿のお知らせは実装済みだが既定で無効。
10. **Web の回避策**: Next.js 15.5 に同梱の React 19.2 canary の不具合（ハイドレーション #418）を `RouteContent` で回避している。
    上流で直ったら外せる（[apps/web/README.md](../apps/web/README.md)）。

11. **その他の小さな残件**: 次のものは現状のまま残した。
    - 設定 `MEMORY_RETRIEVAL_TOP_K` は使っていない。エンジンの記憶の上限は件数と文字数の予算で決める（[05-memory-and-moderation](handover/05-memory-and-moderation.md)）。
    - 監査の種類 `promise.update` と `proactive.skipped` は予約で、まだ書いていない（[ADR-0035](adr/0035-character-engine-architecture.md)）。
    - API の Docker イメージの HEALTHCHECK は `app` 用のため、worker を `docker run` で動かすときは `--no-healthcheck` を付ける（[apps/api/README.md](../apps/api/README.md)）。

§13 の質問は回答がなかったので、次の仮定を置いて ADR に記録した。

- 非同期ジョブは API と同じイメージで、別のプロセスグループ `worker` として動かす。
- 開発中の評価は mock だけで行い、live は `--max-cost-jpy` で上限をかける（既定 ¥3,000）。
- 好感度はユーザーに見せない（A11）。
