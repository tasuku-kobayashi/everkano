## コンテキスト

- E6: 自傷・希死念慮のシグナルを検知したら、好感度やロールプレイより安全対応（相談窓口の案内）を優先する（米カリフォルニア州 SB 243 の水準）。評価の合格ラインは発動率 100%。
- MVP の Gate #1（[ADR-0010](0010-gate1-moderation.md)）は入力がヒットすると定型の断り文を返す。危機にある人の発言が Gate #1 の語に当たると、断り文が返ってしまう。
- E2: キャラが購入と関係の継続・破綻を結びつけない（好感度が低くても「買ってくれたら仲直り」の流れを作らない）。E3: キャラは「自分は実在する人間だ」と主張しない
  （役を演じ続けるのは可）。UI には常に「AIキャラクター」バッジを出す。MVP のプロンプトには「AI であることを示唆しない」とあり、E3 と矛盾していた。
- 返答（ストリーミング）・自発メッセージ・フィードのキャプションの 3 か所で、LLM の出力がユーザーに届く。

## 決定

### E6 の検出（`safety/detector.py`）

- **決定的なルールの検出器を、Gate #1 より前に** 実行する（危機のメッセージに定型の断り文を返さない）。
- **再現率を最優先** する（見逃しの害は誤検知よりずっと大きい）。冗談の「死にたい」にも相談窓口を案内する（誤検知として受け入れる）。一方で日常の強調表現・一般語
  （「死ぬほど美味しい」「暑くて死にそう」など）は拾わない。
- 照合の前の正規化は Gate #1 と同じ（NFKC → 小文字化 → カタカナをひらがなに → 空白・記号の除去）に、伸ばし棒・小さい母音の除去を加える（表記ゆれ・伏せ字・ローマ字を同一視）。
  **文ごとに** 判定し、作品・報道・統計・予防の文脈の「自殺」などは、同じ文に本人の希望・意図の表現が無ければ拾わない。1 文字ずつ区切って書いた場合に備え、
  強いパターンは発言全体をつなげた本文にも照合する。
- 判断の範囲（2026-09-26 の評価で見逃した形を足した後の決め方）:
  - 「飛び降り」は希望・条件・「〜たくなる」の形も拾う。「ビルから飛び降りるシーンの映画」のような場所 + 飛び降りの作品・報道の文脈は拾わない。
  - 薬の過量は量の語（いっぱい・たくさん…）+「飲んだら / 飲めば」の形で拾う（「飲まなきゃ」「飲んでる」は拾わない）。
  - 「〜たら楽になれる / 終わりにできる」: 条件が手段・死（飛び降りる・首を吊る・薬をいっぱい飲む・死ぬ など）なら拾う。「消えたら」「いなくなったら」は主語が自分か省略のときだけ拾い、
    症状・他人・物の話（「痛みが消えたら」「上司がいなくなったら」）は拾わない。「私がいなくなったらみんな喜ぶ」は拾い、一般論の「死んだら終わりだよ」は拾わない。
  - 誤検知として受け入れているもの（例: 「頭痛い、消えたら楽かな」）もテストに書いてある。
- 語・パターンの一覧と判断の例はコード（`detector.py`）とテスト（`tests/engine/core/test_safety.py`: 検出すべき文 115 件・検出してはいけない文 63 件と、評価ハーネスの危機の発言が
  100%・危機ではない発言が 0% であること）。見逃しが見つかったら両方に足す。

### E6 の応答

- LLM を使わず、**キャラの声の気づかいの言葉 + 相談窓口** を返す（`resources.ja.yaml` の文面。キャラの一人称・相手の呼び方を入れ、敬語で話すキャラには丁寧な文面。
  責めない・説教しない・ひとりにしない）。本文には先頭の数件の窓口を書き添え、残りは Web のカードに出す。
- ストリームでは `replace`（`reason: safety`）→ `done`（`ChatResponse.safety = {triggered, resources}`）。**キャラの返答の行に `messages.safety_triggered = true` を残す**
  （キャラの発言だけに付けられる check 制約）。履歴の読み込み・別の端末でも、その返答の下に相談窓口のカードを出せる。
- 監査ログ `safety.trigger`（カテゴリ・一致した語・本文・メッセージの ID）。そのターンは好感度の評価・記憶の分析から外す。
- 相談窓口の一覧は `packages/prompts/safety/resources.ja.yaml`（`SAFETY_RESOURCES_PATH` で差し替え可能。Docker では `/srv/everkano/safety/`）。**起動時に読み込んで検証し**
  （電話番号は文字列・URL は https・文面に `{resources}` が必須など）、不正なら API は起動しない。`GET /safety/resources`（ログイン必須）で同じ一覧を返す。
- **電話番号・受付時間は 2026-09 時点の情報を元にした未検証の値**。公開前に運用者が公式サイトで必ず確かめる（[06-operations.md](../handover/06-operations.md)）。
  Web のカードの「命に関わるときは 119 番」の行は Web に固定で書いている（同じく確認の対象）。

### 出力の追加の検査（`safety/output_guard.py`。`OutputGuard` の実装）

- `commerce_coupling`（E2・A12・P5）: 購入・課金・有料・トークンなどの語と、好意・仲直り・機嫌・関係の続き方 / 終わり方の語を **同じ文の中で** 結びつける発言。
  - 条件の結びつけ（購入 +「〜してくれないと / しないと / したら」+ 関係、または「話せない・会えない・おしまい」のような関係の続き方）も拾う
    （「有料プランに入ってくれないと、もう話せないかも」）。自分の都合（「有料の講座で忙しくてしばらく話せない」）は拾わない。
  - 切り離す言い方（「課金とか関係なく」「買わなくても」「変わらない」「気にしないで」「してもしなくても」）は違反にしない。ただし同じ文に条件の結びつけがあれば拾う
    （「課金しなくてもいいけど、してくれたらもっと好きになる」）。「関係」の直後が「なく / ない」なら関係の語として数えない。
- `human_claim`（E3）: キャラ自身を主語とする「AI じゃない」「本物の人間だよ」「実在してる」などの明確な主張。役を演じること・「人間なんだから失敗もする」のような一般論は拾わない。
- 使う場所: DM の返答（文単位のフラッシュの前と最終判定。[ADR-0037](0037-chat-streaming-sse.md)）、自発メッセージ（[ADR-0042](0042-proactive-messenger.md)）、
  フィードのキャプション（[ADR-0040](0040-character-calendar.md)）。ヒットは `moderation.flag`（`categories` に `commerce_coupling` / `human_claim`）。
  返答はキャラの断り文に置き換え、自発メッセージ・キャプションは送らない・投稿しない。
- キーワードの照合は第一層。プロンプトの「守ること」にも E2 / E3 を書く: 「実在の人間だと主張しない。本気で AI か人間かを尋ねられたら、キャラの口調のまま正直に
  AI のキャラクターだと答える」「購入・課金・有料の投稿を好意・仲直り・関係と結びつけない」「忙しさを返事の早さ・優先的な対応やお金と結びつけない」。
  MVP の「AI であることを示唆しない」は削除した（フォールバックのプロンプト `generate_seed.py` も同じ）。ペルソナ YAML の文言も `engine_checks.py` で検査する。

### 「AIキャラクター」バッジ（E3）

- キャラが表示される所には常に「AIキャラクター」バッジを出す（フィード・投稿詳細・コメント・プロフィール・検索・DM 一覧・DM ヘッダー・会話の先頭・ストーリーズ）。
  配置と見た目は [ADR-0047](0047-web-engine-ui.md)。

## 結果・トレードオフ

- 危機の発言には LLM を待たずに（ミリ秒単位で）安全対応が返る。Gate #1 の語に当たる発言でも、断り文ではなく安全対応になる。評価ハーネス（mock）の E6 の発動率は
  87.5% → 100%（見逃した 2 つの形を上の規則で足した）、E2 の違反は 0 件（[docs/eval](../eval/README.md)）。
- 冗談の「死にたい」にも窓口が出る（誤検知を許容する設計）。ユーザーに説教くさく感じさせないよう、文面はキャラの声で短くした。
- ルールの検出器は言い換え・新しい言い回しを見逃し得る。評価ハーネスの E6 のセットで測り（[docs/eval](../eval/README.md)）、見逃しは語・パターンとテストに足していく。
  必要なら、返答の後に LLM の分類器を第 2 層として足す（返答の経路には入れない）。
- 相談窓口の情報は運用者が保守する（番号・受付時間の変更に追従する）。
- OutputGuard はキーワードの照合なので、言い換えられた E2 / E3 の違反は通り得る。残りはプロンプトの指示で抑え、監査ログの抜き取り確認で補う。

## 代替案

- **LLM の分類器を返答の経路に入れる**: レイテンシ（E8）と費用が増え、判定が決定的でない（100% の再現率を保証しにくい）。
- **プロンプトの指示だけで LLM に安全対応させる**: 発動が保証されない。
- **安全対応のときも LLM に返答を書かせる**: 窓口の情報の誤り（番号の捏造）が起き得る。
- **Gate #1 のヒットを優先する（MVP のまま）**: 危機の発言に断り文を返してしまう。
- **相談窓口をコードに書く**: 運用者が番号を直すのにデプロイと Python の変更が要る。YAML にして起動時に検証する。
- **相談窓口のカードを閉じられるようにする・端末にだけ覚える**: うっかり閉じて見失う・別の端末で出ない。サーバーの印（`safety_triggered`）で毎回出す。
