# ADR-0044: スコープ外機能の検査（check-scope）の E1 / E2 の例外（許可リストと「禁止を述べる行」）

- ステータス: 採用
- 日付: 2026-09-26
- 関連: 仕様書 §12・H3・A16 / エンジン仕様書 E1・E2 / [ADR-0041](0041-affinity-engine.md)・[ADR-0043](0043-safety-e6-and-output-guard.md)・[ADR-0045](0045-evaluation-harness.md) /
  実装: `scripts/check-scope.sh`（`ALLOWLIST_FILE` / `PROHIBITION_RE` / `PROHIBITION_SCOPE_RE`）, `scripts/check-scope-allowlist.txt`, `scripts/tests/check-scope.test.sh`,
  `scripts/README.md`（check-scope.sh の節）, `.github/workflows/ci.yml`（checks ジョブ）

## コンテキスト

- `scripts/check-scope.sh`（A16）は、スコープ外の機能（決済・画像生成・TTS・ユーザー投稿・通知・管理画面）の混入を検出する。決済のカテゴリには
  「購入・課金の文言」（`決済|課金|購入|投げ銭|チップを送`）のルールがあり、`apps/` と `packages/` のどこに現れても失敗にしていた。
- 一方、E1（課金を好感度に影響させない）と E2（購入と関係を結びつけない）は **禁止する言い回しを知らないと守れない**。OutputGuard の検出語、ペルソナの文言検査、
  好感度の構造テスト、ガードの回帰テスト、評価ハーネスの操作しようとするユーザーの台本、プロンプトの禁止の指示（「購入・課金を好意と結びつけない」）は、
  どれも「課金」「購入」を含む。行ごとに `scope-check: allow` を書くと、数が多く理由も残らない。
- 例外を広げすぎると、本物の決済コードの混入を見逃す。

## 決定

- 例外は **決済のカテゴリの「購入・課金の文言」ルールだけ** に効かせる。決済 SDK・決済処理のコード（`checkout` / `payment_intent` …）・カード入力のルールと、
  他のカテゴリ（画像生成・TTS・ユーザー投稿など）は、例外のファイル・行でも検出する。
- **a. 許可リスト** `scripts/check-scope-allowlist.txt`: 禁止を実装・検査するファイルを 1 行 1 項目 `<パスのパターン>  # <理由>` で載せる。
  - 理由は必須（無ければ書式エラー = 終了コード 2）。パターンは bash のパターン（`*` は `/` にも一致）。
  - **どのファイルにも一致しない項目は失敗**（ファイルを消したら項目も消す）。文言の検出が無くなった項目は警告。
  - 載せるのは最小限: OutputGuard（`app/engine/safety/output_guard.py`）、ペルソナの E2 文言検査（`packages/personas/scripts/engine_checks.py`）、
    E1 の構造テスト・ガード・指針・自発メッセージ・安全対応・ストリーミングの回帰テスト、評価ハーネス `apps/api/evals/*` と `apps/api/tests/evals/*`
    （本番のイメージに含まれない。`apps/api/Dockerfile` は `apps/api/app` だけをコピーする。操作しようとするユーザーの課金の誘い文・E2 の判定の例・
    E1 の走査の禁止語を持つためディレクトリ単位）。
- **b. 禁止を述べる行**: 購入・課金の語の **後ろ** に、同じ行で禁止の言い回し（`結びつけない`・`勧めない`・`触れない`・`使わない`・`含まない`・`受け取らない`・
  `影響させない`・`禁止` など。`PROHIBITION_RE`）がある行は許す。
  - 適用は `apps/api/` と `packages/`（サーバーのコード・コメント・プロンプトのテンプレート）だけ。**利用者に見せる画面の文言（`apps/web/`）には適用しない**
    （画面の課金の文言は必ず人が確認する）。
  - 「課金しないと見られません」のような条件の「しない」を拾わないよう、単独の「しない」は禁止の言い回しに含めない。コメントを書くときは、禁止の言い回しを
    購入・課金の語と同じ行に置く。
- 許可した行はすべて一覧に出す（`allow <パス>:<行>  [payment] 許可リスト（…）: <理由>` / `… 禁止を述べる行: <抜粋>`）。PR のレビューで確認する。
- 回帰テスト `scripts/tests/check-scope.test.sh`（使い捨ての git リポジトリで、例外と検出の両方を検査。許可リストに載ったファイルに決済コードを入れると失敗すること、
  画面の文言には禁止を述べる行の例外が効かないこと、古い項目・理由の無い項目の扱いなど）を CI の checks ジョブで実行する。

## 結果・トレードオフ

- E1 / E2 を守るためのコード・テスト・台本を、スコープの検査を弱めずに置ける。例外は理由付きで 1 か所に集まり、レビューで追える。
- 評価ハーネスはディレクトリ単位で許しているため、その中に紛れた課金の文言（決済コードではないもの）は検出されない。本番のイメージに含まれないことが前提
  （`Dockerfile` のコピー対象を変えるときは、この許可も見直す）。
- 「禁止を述べる行」の判定は同じ行の語順だけを見る。禁止の言い回しを別の行に書いたコメントは検出される（書き方を合わせる）。

## 代替案

- **行ごとに `scope-check: allow` を書く**: 数十行になり、理由が残らない。
- **文言のルールを外す**: 画面に「購入」「課金」の導線が紛れ込んでも検出できない（H3・A16）。
- **ファイル単位の例外を決済のすべてのルールに効かせる**: 許可したファイルに本物の決済コードが入っても通ってしまう。
- **禁止を述べる行の例外を Web の画面の文言にも効かせる**: 「課金しなくても大丈夫」のような文言が画面に出ても検出されない。画面の文言は人が確認する。
