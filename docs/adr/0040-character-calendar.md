## 決定

### 世界の時計（C1・C4。`world.py`。DB を使わない純粋関数）

- 日本時間・曜日・季節・時間帯。祝日は **`holidays` パッケージ**（`country_holidays("JP")`。振替休日・国民の休日を含み、春分・秋分は天文計算による推定。
  オフラインで動く）。平日（月〜金）だけ働くキャラは、祝日を日曜の過ごし方にする。
- 季節の行事は自前の表（関東・東京の平年に寄せた「おおよその期間」）: 梅雨 6/7〜7/19（気象庁の関東甲信の平年値）、花見 3/25〜4/10、紅葉 11/15〜12/7、
  夏祭り・花火 7/20〜8/31、お盆 8/13〜8/16、年始 1/1〜1/3、年末 12/28〜12/31、クリスマス 12/24〜25、ゴールデンウィーク 4/29〜5/5（振替休日が続けば延ばす）など。
  中秋の名月は国立天文台 暦計算室の公表値の表（2024〜2035 年。表の外の年は出さない）、節分は立春の前日（2025・2029・2033 年は 2/2）。

### 予定の生成（C2・C3・C4。`generator.py`）: ルールだけ・LLM を呼ばない

- 予定は **ペルソナが書いたテンプレートからだけ** 作る（キャラの性格との一貫性はここで担保する）:
  - ルーティン: `life.routine` を曜日ごとに展開（日をまたぐ睡眠を含む）。
  - 単発の出来事: `life.events` のテンプレートを週ごとに抽選する。乱数の種は hash(キャラ, ISO 週, テンプレート) なので、同じキャラ・同じ週は何度生成しても同じ
    （評価で再現できる）。`weekly_probability`・曜日・月を守る。最短間隔 M 日（`min_interval_days`）のあるテンプレートは、L = ⌈(M + 7) / 7⌉ 週の「期間」ごとに
    最大 1 回、確率 1 − (1 − p)^L で抽選し、日付は期間の最初の 7L − M 日から選ぶ（隣り合う期間の出来事は必ず M 日以上離れ、前の期間の結果を見ずに決まる）。
    期間の区切りはキャラ × テンプレートごとにずらす。
  - 行事: `seasonal[].attends` の行事をその年の期間の 1 日に入れる。誕生日: `life.birthday` の夜。
- 生成は `calendar.ensure_schedules`（1 時間ごと）が昨日〜`ENGINE_CALENDAR_DAYS_AHEAD`（既定 7）日先を作る（`generated_for` で日ごとに冪等）。
  まだ生成していない日の状態が要るときは、生成器の結果をその場で使う。

### データの持ち方: 1 件 1 行（`character_events`）

- 繰り返しの規則（RRULE）ではなく、**予定の 1 回ごとに 1 行** を持つ（7 日先までの窓なので行は増えすぎない）。`kind`（routine / oneoff / seasonal / promise）、
  `visibility`（public = キャラの実際の生活 / user = 特定のユーザーとの約束）、`source`・`source_key`（生成元）、`participants`（C10）、`post_id`、`meta`。
- 状態・キャラ側の記憶・投稿・約束が具体的な予定の ID を参照でき、DB の排他制約が使え、ルーティンの切り取り・例外が単純になる。

### 一貫性（C11）

- 重なりの優先度: 行事・誕生日 > 単発 > ルーティン。ルーティンは重なる部分を切り取り（分割）、30 分未満の残りは落とす。単発どうし・行事どうしが重なれば後のものを落とす。
- 日付 D の予定は D−1〜D+1 の候補をまとめて解決してから D の分を取り出す（日をまたぐ予定を、どの日から生成しても同じ結果にする）。
- DB に既にある予定（手で入れたものを含む）とぶつかる分は切り取る（既存を優先）。キャラ単位のアドバイザリーロックで同時の生成を直列にする。
- 最後の守りは DB の排他制約 `character_events_no_overlap`（同じキャラの公開の予定は時間が重ならない）。違反した行はセーブポイントの中で落とし、`calendar.conflict` を残す。
- 検査器 `check_consistency()`（`consistency.py`）: error（評価で 0 件を求める）= `overlap`・`not_from_template`・`outside_template`・`min_interval`・
  `memory_mismatch`・`memory_before_end`・`memory_cancelled_event`・`state_mismatch`、warning = `sleep_missing`・`sleep_short`・`work_on_holiday`・`not_sampled`。
  テストと評価ハーネスが使う。ペルソナを書く人には `lint_life_spec()`（ルーティンの重なり・語彙に無い画像タグ）。

### 今の状態と返答への反映（C5・C6。`state.py`）

- 今の状態 = 今の時刻を含む公開の予定（無ければペルソナの「予定の無い時間の過ごし方」）。活動・場所・気分・忙しさ（0 ひま〜3 手が離せない / 睡眠）・
  表示用のラベル `status_label`、次の予定、直近 48 時間に終わった出来事。
- `calendar.tick`（5 分ごと）が `character_states` を更新する（予定が変わったときだけ `calendar.state_change`）。
- 返答への反映は **忙しさで返答の長さだけを変える**（ゆっくり / ふつう / 短め / ごく短く・睡眠中は眠そうに）。プロンプトには今・次・直近の予定を入れる。
  **返答を遅らせる演出はしない**（ユーザーを待たせない。§5.3）。状態の指示にお金・購入の話は入れない（E2）。
- DM のヘッダーに `status_label` を出す（[ADR-0047](0047-web-engine-ui.md)）。クライアントに見せるのは `status_label`・`busyness`・`updated_at` だけ。

### 過ぎた予定とキャラ側の記憶（C9）

- `calendar.tick` が終わった予定を `done` にし（`calendar.event_done`）、目立つ出来事（単発・行事。ルーティンは投稿したものだけ）を全ユーザー共通のキャラ側の記憶
  （`character_memories`、`kind = event`・`user_id` null・`source_event_id`・埋め込みあり）にする（`character_memory.create`）。「先週の旅行どうだった？」に答えられる。

### フィード投稿（C7。`captions.py`・`service.py`）

- 予定が終わったとき、予定の投稿確率に対して決定的な乱数で投稿するかを決める。キャプションは LLM（用途 `feed_caption`・`LLM_MODEL_CAPTION`）で、ペルソナの口調・
  絵文字の決まりに合わせて作る。**Gate #1 + キャラの NG ワード + リンクの差し止め + OutputGuard（E2 / E3）** を通らなければ投稿せず、理由と使用量を監査ログに残す。
- 画像は事前に用意したプール `post_image_pool`（タグ付き。`infra/supabase/seed_engine.sql`）から選ぶ（最近使っていないもの > そのキャラ用 > タグの一致 > 決定的なハッシュ）。
  タグの語彙は `engine/types.py` の `TAG_VOCABULARY` 1 つ（ペルソナの `post_tags`・キャプション・プールで共通）。
- 公開時刻は予定の終わりの少し後。1 キャラ 1 日（JST）あたりの投稿数の上限、終わってから時間がたった予定は投稿しない（停止からの復帰でまとめて投稿しない）など、
  量の上限は `CalendarConfig` に持つ。`posts.source_event_id` と `character_events.post_id` で予定と投稿を結ぶ。

### 約束の登録（C8）

- 返答の後のジョブが、新しい約束を `visibility = user`・`kind = promise` の予定にする（`sync_promise_events`。期日の精度が `datetime` なら 1 時間、`day` ならその日 1 日。
  `week` / `month` / `unknown` は登録しない）。約束の期日・状態が変われば予定を移す・取り消す（`calendar.promise_event`）。`promises.event_id` に記録する。
  特定のユーザーとの予定なので、公開の予定の重なりの制約の対象外。

### キャラ同士の予定（C10）

- 構造だけ: 単発の出来事のテンプレートが他の有効なキャラの名前に触れていれば `participants` に入れる。相手のキャラのカレンダー・フィードへの反映はしていない。

## 結果・トレードオフ

- 予定の生成に LLM を使わないので、予定の費用は 0。LLM を使うのはキャプション（全ユーザー共通の固定費）だけ。同じ入力なら同じ予定になり、評価で再現できる。
- 予定の種類はペルソナが書いたテンプレートの範囲に限られる（テンプレートを書く手間がかかる。`packages/personas/README.md` の手順と `engine_checks.py` の検査）。
- 複数日にまたがる予定（旅行など）は表せない（日帰りとして書く）。行事の予定には忙しさ・ラベルを書けるが、既定値のものもある。
- C10 のキャラ同士の共有は未完（相手側に反映しない）。精度が週・月・不明の約束はカレンダーに入らない。
- 予定から作った投稿は公開時刻が未来のことがあり、その間は RLS で見えない（予約投稿と同じ）。
- 画像プールのシードはプレースホルダ（外部の URL）。本番では実際の画像を B2 / Bunny に置き、プールの行を差し替える（[06-operations.md](../handover/06-operations.md)）。

## 代替案

- **LLM で週ごと・日ごとの予定を作る**: 表現は豊かだが、ペルソナと矛盾する予定を作り得て、検証が要り、毎週費用がかかる。
- **ルール + LLM の味付け（単発の出来事の提案など）**: 検証の負担が残る。まずルールだけにした。
- **繰り返しの規則（RRULE）で持つ**: 例外・上書きが複雑になり、DB の排他制約が使えない。状態・投稿・約束が具体的な予定を参照できない。
- **最短間隔の判定に DB の前回の出来事を見る**: 生成の順番で結果が変わり、再現できない。
- **前の週の抽選結果だけを見て間隔を守る**: 頻度の高いテンプレートがほとんど起きなくなった（抽選が互いを打ち消す）。
- **内閣府の祝日 CSV・カレンダー API を取り込む**: 外部への通信と更新の運用が要る。`holidays` はオフラインで振替休日まで扱える。
- **祝日を手で表にする**: 毎年の保守が要る。
- **忙しいときに返信を遅らせる演出**: ユーザーを待たせる（§5.3・E8）。返答を短くすることで状態を表す。
