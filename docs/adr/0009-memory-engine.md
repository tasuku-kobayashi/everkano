# ADR-0009: メモリエンジン設計（ターン定義、抽出の並行実行、重複排除、ユーザー編集の保護、中期要約）

- ステータス: 採用（抽出の並行実行・再注入の方式・中期要約の実行方法（BackgroundTask）は [ADR-0038](0038-memory-engine-v2.md) により置き換え。埋め込みの障害時の扱いを [ADR-0022](0022-embedding-failures-and-audit-additions.md)、記憶の件数上限を [ADR-0024](0024-memory-capacity-per-pair.md)、履歴の文字数の上限と中期要約のチャンク化・失敗時のバックオフを [ADR-0028](0028-llm-input-budgets-and-summary-retries.md)、ユーザーが削除した記憶の保護を [ADR-0039](0039-user-edited-memory-protection.md) で追補）
- 日付: 2026-09-25
- 関連: 仕様書 §7・§9 / [ADR-0005](0005-vector-index-and-exact-memory-search.md) / [ADR-0019](0019-chat-deadline.md) / 実装: `apps/api/app/services/memory.py`, `apps/api/app/services/chat.py`, `apps/api/app/services/prompt.py`, `packages/prompts/templates/`

## コンテキスト

仕様書 §9 は短期（直近 30 ターン）・中期（50 ターンを超えたら要約）・長期（重要度スコアリング → 埋め込み → pgvector で再注入）の
3 層と、「ユーザー編集済みの記憶は自動上書きしない」を求めている。「ターン」の数え方、抽出のタイミング、重複の扱い、要約の範囲は
仕様書に無く、実装で決める必要があった。応答の遅延（DM の体験）とコストも考慮する。

## 決定

### ターンと短期メモリ

- **1 ターン = ユーザー発言 1 件 + キャラ返答 1 件（メッセージ 2 件）**。短期メモリは直近 `MEMORY_SHORT_TERM_TURNS`（30）× 2 = 60 件。
- 短期の履歴は system プロンプトに文字列で埋め込まず、`user` / `assistant` の会話履歴メッセージとして渡す（話者の取り違え防止）。
  テンプレートの `{short_term}` には注記（前回から日が空いていればその日付）だけを入れる。同じ role の連続は 1 メッセージに結合する。

### 長期メモリの抽出（§9.2）

- `/chat` の応答生成と **並行して**（`asyncio` のタスク）1 回だけ LLM を呼び、直近 6 件の文脈 + 今回の発言から記憶候補を JSON で抽出する
  （`memory_extraction.ja.txt`、`temperature 0`）。候補は 1 発言あたり最大 5 件、本文 500 文字まで。重要度 0〜1 と観点
  （emotion / personal / promise / relationship）を持つ。
- 重要度が `MEMORY_IMPORTANCE_THRESHOLD`（0.6）以上の候補だけを埋め込み、保存する（`source_message_id` = ユーザー発言）。
- 抽出の失敗は `llm.error`（`purpose=memory_extraction`）として記録し、チャット自体は成功させる（「記憶すべきことが無かった」と区別できる）。

### 重複排除とユーザー編集の保護

- 保存前に、同じペアの既存の記憶（`summary` タグを除く）から最も近いものを厳密検索し、コサイン類似度が `MEMORY_DEDUP_SIMILARITY`（0.92）以上なら:
  - その記憶が **`is_user_edited = true` なら何もしない**（ユーザーが書いた / 直した記憶は自動処理で決して上書きしない）。
  - そうでなければ本文・埋め込みを新しい候補で更新し、重要度は大きい方を取る（`memory.update`、`memories_created` には数えない）。
- それ以外は新規作成（`memory.create`）。ユーザーがメモリパネルで追加・編集した記憶は `is_user_edited = true`。

### 再注入（§9.3）

- ユーザー発言を埋め込み、ペア内の厳密検索で上位 `MEMORY_RETRIEVAL_TOP_K`（5）件 → 重要度で再ランク + 最新の要約 2 件（[ADR-0005](0005-vector-index-and-exact-memory-search.md)）。
  この ID の一覧が `ChatResponse.memories_used`。
- プロンプトでは 1 行 1 件。`secret` タグ（メモリパネルの「二人だけの秘密」）は `（二人だけの秘密）`、`summary` タグは `（これまでの会話の要約）`
  を先頭に付け、末尾に記録日（日本時間）を付ける（記憶の中の「来週」「明日」を記録日基準で解釈させるため）。

### 中期要約（§9.1）

- 応答を返した後の FastAPI BackgroundTask で判定する。`summary_cursor` より新しいメッセージが 2 × `MEMORY_SUMMARY_TRIGGER_TURNS`（100）件を
  超えたら、**短期ウィンドウ（直近 60 件）より古い未要約分** を 1 件の要約記憶にする（`tags={'summary'}`、重要度 0.7、埋め込みあり、
  `temperature 0` の JSON 出力）。`summary_cursor` を要約した最後のメッセージの `created_at` に進め、`memory.summary` を記録する。
- 同時実行の対策: 同じプロセス内は会話単位のフラグで二重起動を防ぎ、保存時は `select ... for update` でカーソルが変わっていないことを確認する
  （他のワーカーが先に要約していたら何もしない）。

### Gate #1 で差し止めた発言の扱い

- 入力が差し止められた発言も `messages` には保存する（会話の記録として。[ADR-0010](0010-gate1-moderation.md)）。ただし以後の LLM への履歴と
  抽出の文脈では本文を「（不適切な発言のため省略）」に置き換え、中期要約からはそのターン（直後の定型返答を含む）ごと除く
  （`sanitize_history`。Gate #1 は決定的なので、保存済みの本文にもう一度かければ同じ判定になる）。

### メモリパネル（§9.4）

- 一覧は `GET /memories`（重要度 → 新しい順、最大 500 件）。UI の優先度は 3 段階（低 0.3 / 中 0.6 / 高 0.9。追加時の既定は中）。
  API に重要度を渡さずに追加した場合の既定は 0.7。記憶の本文は Gate #1（入力）を通す。
- 返答で新しい記憶ができると、DM 画面に「〇〇があなたのことを覚えました」を出す（タップでメモリパネル）。

## 結果・トレードオフ

- 抽出を並行にしたので、応答の遅延は「返答生成」と「抽出」の長い方で済む（直列より短い）。ただし 1 往復で LLM を 2 回呼ぶコストがかかる。
- 返答の直後に `memories_created` を返せるので、UI で「覚えました」を即時に出せる。
- ユーザー編集済みの記憶と内容が近い候補は捨てるため、ユーザー編集済みの記憶同士の重複は起こり得る（ユーザーが自分で消す）。
- 要約記憶は約 40 件のメッセージごとに 1 件増える。常に入るのは最新 2 件だけで、古い要約は類似度検索で拾われたときだけ入る。
- 中期要約は BackgroundTask なので、完了前にマシンが再起動すると実行されない（次の送信で再判定されるので、取りこぼしは次回に回収される）。
- 埋め込みの方式を変えたら全件の再埋め込みが必要（`scripts/reembed_memories.py`。冪等・バッチ・本文が変わった行は上書きしない）。

## 代替案

- **抽出を返答の後に直列で行う**: 実装は単純だが、1 往復の遅延が LLM 2 回分になる。
- **抽出をレスポンス後のバックグラウンドで行う**: 遅延は増えないが、`memories_created` を返せず「覚えました」の表示ができない。次の発言までに
  保存が終わる保証も無い。
- **LLM に重複判定させる**: 精度は上がり得るが、呼び出しが増える。埋め込みの類似度で十分とした。
- **毎ターン要約する / 固定件数ごとに全体を要約し直す**: コストが大きい。未要約分だけを閾値で要約する。
