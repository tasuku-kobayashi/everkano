# ADR-0030: Web のデータ取得（既存の DM 会話は API を経由せずに開く・差分での取りこぼし回収・遷移先の先読み・購読の絞り込み）

- ステータス: 採用
- 日付: 2026-09-26
- 関連: 仕様書 §5.4・§5.5・§14 / [ADR-0002](0002-data-access-split.md)（本 ADR で追補）・[ADR-0016](0016-realtime-anon-primary-key-grant.md)・[ADR-0029](0029-web-network-failure-policy.md) /
  実装: `apps/web/lib/queries/dm.ts`（`resolveConversation` / `prefetchDmConversation` / `useDmThreadsRealtime` / `dmThreadsRealtimeFilter`）,
  `apps/web/lib/queries/messages.ts`（`resyncMessages` / `CATCH_UP_LIMIT`）, `apps/web/lib/queries/prefetch.ts`, `apps/web/lib/queries/comments.ts`（`COMMENTS_LIMIT`）,
  `apps/web/e2e/dm.spec.ts`・`prefetch.spec.ts`

## コンテキスト

ADR-0002 は「読み取りは Supabase へ直接、ユーザー由来テキストの書き込みは Python API」と決めた。納品前の検査で、その範囲の中で
通信の回数と順番に無駄があり、スマホ回線で待ち時間が伸びていることが分かった。

- DM を開くたびに `POST /conversations`（Python API）→ 結果を待ってから `messages` の取得、の 2 往復が直列だった。さらに 1 ページ目を 2 回取得し、
  `list_dm_threads` も 1 回開くだけで 4〜5 回呼ばれていた。API が止まっていると既存の会話の履歴すら読めなかった。
- 画面への復帰や Realtime の再接続のたびに、無限クエリの再取得で読み込み済みの全ページを 1 ページずつ順に取り直していた（300 件 = 10 ページ読み込んだ
  会話で、1 回の復帰につき 11 リクエストが直列）。
- DM 一覧は `messages` の INSERT を **フィルタなしで** 購読していた。RLS で自分の分しか届かないとはいえ、全ユーザーの全メッセージについて
  Realtime サーバーが一覧を開いている全員分の認可判定をしていた。
- 動的ルート（`/posts/[postId]`・`/c/[handle]`・`/dm/[characterId]`）への遷移では、ルートの JS の読み込みと描画が終わるまでデータの取得が始まらなかった。
  投稿詳細・プロフィールでは、キャラ本体の取得を待ってから投稿数やコメントを取りに行っていた。
- コメントは古い方から 500 件を取っていたため、コメントの多い投稿では新しいコメント（投稿した直後の自分のコメントを含む）が再読み込みで消えていた。

## 決定

- **既存の DM 会話は API を経由せずに開く**: 会話画面は、まず自分の会話を supabase-js で直接読む（RLS: 本人の会話だけ）。その際、最新 1 ページ（30 件）の
  メッセージを埋め込みで同時に取得し、メッセージのキャッシュを埋める（1 往復で表示できる）。**会話が無いときだけ** `POST /conversations` で作る
  （初回の挨拶の保存は API の仕事のまま）。API が停止・再起動中でも既存の会話の履歴は読める。
- **取りこぼしの回収は差分だけ**: Realtime の購読開始・再接続、画面・オンラインへの復帰のときは、キャッシュの最新メッセージより新しいもの
  （5 秒遡って取り、id で重複排除）だけを取得して先頭ページへ差し込む（`resyncMessages`）。読み込み済みのページは取り直さない。
  取りこぼしが `CATCH_UP_LIMIT`（100）件以上なら、差分では埋めずに最新の 1 ページだけを取り直す。
- **DM 一覧の購読は自分の会話に絞る**: `conversation_id=in.(<一覧の会話 ID>)`（最大 100 件。それを超える会話は 30 秒ごとのポーリングとフォーカス復帰で追う）。
  会話がまだ無ければ購読しない。再接続のときだけ一覧を取り直す。既読（`mark_conversation_read`）は 1 往復につき 1 回。
  タブバーの未読バッジは、タブバーを出さない画面（投稿詳細・DM 会話）では取得しない。
- **遷移先の先読み**: リンクに触れた時点（`pointerdown`）で、遷移先の画面と同じクエリ設定（`xxxQueryOptions()`）でデータを取りに行く
  （`prefetchPostDetail` / `prefetchCharacterProfile` / `prefetchDmConversation`）。先読みは読み取りだけにし、**副作用のある API（会話の作成など）は呼ばない**。
  会話がまだ無いキャラの DM は、キャラ情報だけを先読みする。
- **依存しない取得は並行に**: 投稿詳細はコメントの取得を投稿本体の取得と同時に始め、プロフィールは投稿数・グリッドの取得をキャラ本体の取得と同時に始める。
- **コメントは新しい方から 500 件**（`COMMENTS_LIMIT`）を取り、画面では時系列の昇順に並べる。500 件を超える投稿では古いコメントを表示しない（その旨を表示する）。

## 結果・トレードオフ

- 再検査: `/dm/<id>` を直接開いたとき Python API へのリクエストは 0 件、会話（最新ページ埋め込み）1 件 + 差分 1 件。一覧の行をタップした場合は
  先読み済みの 1 ページ + 差分 1 件。E2E（`dm.spec.ts`・`prefetch.spec.ts`・`post-detail.spec.ts`・`profile.spec.ts`）で回帰を検査している。
- 会話の読み取りは RLS に頼る（ADR-0002 の読み取りと同じ）。会話の作成・メッセージの書き込みは引き続き API だけ。
- 差分取得は `created_at`（`clock_timestamp()`）の順序に依存する。ほぼ同時の 2 つの保存の順序の逆転は 5 秒遡ることで吸収する。
- 100 件を超える会話を持つユーザーでは、101 件目以降の会話の新着が一覧に反映されるまで最大 30 秒かかる。
- 先読みは触れただけで通信するので、スクロール中の誤タップでも取得が走る（読み取りだけで、キャッシュの新しさ（staleTime）以内なら何もしない）。
- 500 件を超えるコメントの遡り表示（「以前のコメントを表示」）は未実装。Realtime・作成・削除のキャッシュの形に影響するため、納品後の課題とする。

## 代替案

- **`POST /conversations` を残し、メッセージの取得と並行に投げる**: 会話 ID が分からないとメッセージを取得できないため並行にできない。
- **Next.js のサーバーコンポーネントでデータを取得する**: ADR-0002 のとおり、Next.js のサーバーはアプリのデータを取得しない（ユーザーのトークンを
  サーバーで扱う範囲を増やさない）。
- **無限クエリの `refetch` を使い続け、ページ数を減らす**: 遡って読んだ履歴が消える。差分の方が通信量も少ない。
- **ルートの `loading.tsx` だけで体感を改善する**: 表示は早くなるが、データの取得開始は遅いまま。
