### 5.1 確認した指摘のうち残っている部分

| 項目 | 未対応の理由 | 推奨する対応 |
| ---- | ------------ | ------------ |
| **ログインのボット対策（CAPTCHA）**（セキュリティ・M） | Web のログイン画面が `captchaToken` を送るようになる前に Supabase で CAPTCHA を有効にすると、誰もログインメールを要求できなくなる。Web のウィジェットとホスト版の設定を同時に入れる必要があり、納品直前の変更としては影響が大きい。それまでは、メール送信枠の枯渇によるログイン妨害を受け入れるリスクとした（コードの有効期限は 15 分に短縮済み） | 一般公開の前に、Web に hCaptcha（Turnstile は H8 で不可）を入れて `signInWithOtp` に `captchaToken` を渡し、その後に Supabase の Attack Protection で有効にする。それまでは Auth のログの 429（`over_email_send_rate_limit`）を監視（[ADR-0033](../adr/0033-auth-hardening-password-otp-captcha.md)、[supabase-auth.md](../handover/supabase-auth.md) §5） |

| **SBOM と `LICENSE` の権利者**（その他・L） | `LICENSE` の権利者の名義は開発委託契約の当事者を依頼者に確認する必要がある（現在は「開発委託契約に定める者」）。機械可読な SBOM の生成は CI の変更になるため見送った | 依頼者が名義を確定して `LICENSE` を更新する。DD で求められたら CycloneDX 形式の SBOM（npm と Python の両方）を CI で生成する。依存を更新したら `THIRD_PARTY_NOTICES.md` を再生成する |
